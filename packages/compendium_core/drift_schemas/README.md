# Drift schema dumps

One JSON file per **supported** on-disk schema version — `drift_schema_v20.json`
(the floor) through `drift_schema_v<head>.json` — generated by
`drift_dev schema dump`. Versions below the floor are retired and deliberately
have no dump; see "The floor" below.

They exist so that `test/storage/schema_verification_test.dart` can build a
database at any supported version and check that running the real migration
over it produces the same structure as a freshly created database at head
(issue #828). Nothing else reads them.

`test/storage/generated/` holds the Dart schema classes generated from these
dumps. Both directories are machine-generated; edit neither by hand.

## Why the dumps live in `generated/`

The `generated/` path segment is load-bearing, not tidiness. GitHub excludes
`**/generated/**/*` from Copilot code review, and Copilot refuses outright to
review a pull request exceeding 20,000 changed lines. These dumps are ~26,000
lines on their own, so with them anywhere else **every** schema pull request is
unreviewable — the refusal arrives as a normal-looking `COMMENTED` review whose
body is the only place the failure appears.

Putting genuinely generated files under `generated/` is an accurate description
of what they are, and it keeps the hand-written surface of a schema change
reviewable. Do not flatten this directory back.

## What they are, and what they are not

Each dump is taken from a **real database file**, not from static analysis of
`lib/src/storage/database.dart`:

* Every supported version below head comes from the committed fixture of the
  same name in `test/storage/fixtures/`.
* The head dump comes from a database created on the spot by
  `tool/write_head_database.dart`.

That matters because five entities in this schema are created by raw
`customStatement` DDL rather than being drift-managed — the `dance_fts` FTS5
virtual table and the four lookup indices `dance_figures_move_section`,
`dance_links_dance_id`, `programs_venue_id` and `program_slots_dance_id`. A
dump taken from Dart source contains none of them, which would leave exactly
the entities that are maintained by hand in two places (`onCreate` **and** an
upgrade step) outside the verification. Dumping databases keeps them in scope,
and keeps every file in this directory homogeneous.

A dump is a record of **structure only**. The fixture generators in
`test/storage/fixtures/` seed *realistic data* and back the data-semantics
assertions in `migration_test.dart`; dumps do not replace them and none of them
should be deleted. What dumps replace is the need to hand-derive a *new*
generator for every future version (see "Adding a version").

## The floor: which versions live here

Only versions from `kMinSupportedSchemaVersion` (currently **v20**) up to head
have dumps. Earlier ones were retired (#837, floor raised past v19): `v0.1.0-
beta.6` is the oldest supported release and shipped schema v20, so nothing can
present a database below it that we are willing to migrate — `onUpgrade`
refuses one outright.

`schema_verification_test.dart` asserts the set here is **exactly** floor…head,
so both a missing dump and a lingering retired one are failing tests rather than
silent drift, and `tools/ci/check_schema_migration.py` rejects any PR that
reintroduces a below-floor artefact.

## Adding a version

When you bump `kCompendiumSchemaVersion`, add a dump for the new head. You do
**not** need to write a new `generate_vN_fixture.dart` for schema verification —
that is the cost this directory exists to remove.

`schema_verification_test.dart` fails if a version has no dump, so forgetting
this is a red test rather than a silent coverage hole.

## Regenerating

`drift_dev` cannot run from this workspace. Every release from 2.34.1 onwards
requires `analyzer ^13.0.0`, while `flutter_test` pins `matcher`/`test_api` such
that `test` resolves to a version capping `analyzer` below 13; and 2.34.0 — the
last release compatible with analyzer 12 — does not compile against
`drift >= 2.34.1` (it references a `GeneratedDatabase.allSchemaEntities` getter
that is private there). That break is in `verifier_common.dart`, which
`api/migrations_native.dart` imports, so it takes down `SchemaVerifier` too and
not just the CLI.

None of that matters at test time: the generated schema classes import only
`package:drift/drift.dart` and `package:drift/internal/migrations.dart`, both
already production dependencies. `drift_dev` is needed **only** to produce the
files here, from a throwaway project outside the workspace.

1. Create a scratch project anywhere outside this repository:

   ```yaml
   name: drift_schema_tools
   publish_to: none
   environment:
     sdk: ^3.12.0
   dependencies:
     drift: 2.34.2      # match compendium_core's resolved drift
   dev_dependencies:
     drift_dev: 2.34.5
   ```

   then `dart pub get`.

2. Write a fresh head database, from this package's root:

   ```sh
   dart run tool/write_head_database.dart /tmp/schema-src/head.sqlite
   cp test/storage/fixtures/v*.sqlite /tmp/schema-src/
   ```

3. Dump each database, **from the scratch project**:

   ```sh
   dart run drift_dev schema dump /tmp/schema-src/v20.sqlite \
       <repo>/packages/compendium_core/drift_schemas/generated/drift_schema_v20.json
   # … and so on for each fixture from the floor up, then
   # head.sqlite -> drift_schema_v<head>.json
   ```

   The version in the filename must match the source database's
   `PRAGMA user_version`; pass an explicit filename rather than a directory so
   nothing depends on inferring it.

   **`drift_dev schema dump` and `schema generate` write their output and then
   never exit** — the analysis isolate is left running. Background each
   invocation and kill it once its output file appears.

4. Restore the Dart getter names that a SQL round-trip cannot carry, and
   generate the schema classes:

   ```sh
   # from this package's root
   dart run tool/normalize_schema_dumps.dart drift_schemas/generated /tmp/schema-norm

   # from the scratch project
   dart run drift_dev schema generate /tmp/schema-norm \
       <repo>/packages/compendium_core/test/storage/generated/
   ```

   Step 4a is not cosmetic. `tables.dart` declares

   ```dart
   TextColumn get text_ => text().nullable().named('text')();
   ```

   because `Table` already declares `ColumnBuilder<String> text()`. A dump
   reverse-engineered from SQL derives the getter name `text`, and a generated
   class extending `Table` with a `text` member does not compile
   ("Can't declare a member that conflicts with an inherited one"). drift's main
   table writer honours the source declaration — see
   `late final GeneratedColumn<String> text_` in `database.g.dart` — but its
   schema writer does not. `normalize_schema_dumps.dart` restores it **on a
   copy**, so the committed dumps stay byte-faithful to what `schema dump`
   wrote, and it hard-fails on any future column whose derived getter would
   collide without an override.

5. Verify: `dart format`, `dart analyze`, and
   `dart test test/storage/schema_verification_test.dart`.
